# Один браузерный сервис для всех агентов

Один процесс `alive browser host` владеет одним Fortress-контейнером. Независимые процессы и контейнеры Alive подключаются к нему по приватному Playwright WebSocket-протоколу. Для каждого подключения создаётся отдельный BrowserContext: вкладки, cookies, localStorage и IndexedDB не пересекаются. Каждый агент сохраняет своё состояние в собственном `.alive/`.

```text
Alive A / контейнер A ─┐                      ┌─ контекст A ─ Mini App A
Alive B / контейнер B ─┼─ private host:4330 ────┼─ контекст B ─ Mini App B
Alive C / контейнер C ─┘  один Fortress       └─ контекст C ─ Mini App C
```

Контроллер телефона остаётся у соответствующего агента. Его HTTPS-адрес `publicUrl` и порт 4323 не являются адресом браузерного сервиса. Агент может продолжать обычную работу при открытом пульте и отзывать доступ; приватный вход/ручная проверка сохраняют существующую остановку до возврата управления. Получатель Telegram определяется разговором, а не общим браузером.

## Запуск на браузерном хосте

Нужны Node.js >=22, зависимости проекта и Docker. Установите зависимости, соберите проект и установите официальный закреплённый OSS-образ по [инструкции Fortress](../fortress/README.ru.md). На одном хосте выполняется один набор команд:

```sh
pnpm install --frozen-lockfile
pnpm build
node dist/index.js browser setup --engine fortress --driver patchright --headless true --cdp-env "" --executable-env ""
node dist/index.js browser host --background
node dist/index.js browser host-status
```

Используется OSS Fortress 151.0.7908.0 под BSD-3-Clause; аккаунт, активация и license token не нужны. Новый `latest` не используйте: это уже другая лицензия/ветка. Сервис стартует независимо от основного агента; не запускайте его в каждом агентском контейнере. По умолчанию он слушает `127.0.0.1:4330`, создаёт приватный файл `.alive/modules/browser/shared-host/token` (600), а также отдельные `runtime.json`, `endpoint.json`, `logs/` и профиль внутри `shared-host/`. В выводе нет значения токена. Для другого размещения файла есть `--token-file /absolute/private/path`. `--max-clients 8` задаёт общую вместимость.

Для systemd скопируйте [пример сервиса](alive-browser-host.service), изменив пользователя, путь проекта и путь Node. Используйте `--foreground`, а управление рестартами поручите systemd. Docker доступен только этому сервису; агентам не нужен Docker socket. Пример не устанавливается автоматически и не меняет службы компьютера.

## Подключение локального агента

Если агент уже работал с отдельными Fortress-профилями, сначала выполните перенос при остановленном агенте:

```sh
node dist/index.js stop
node dist/index.js browser migrate-shared
```

Импорт не заменяет существующий `shared-storage.json` и сохраняет исходные профили. Он переносит cookies и доступные открытые storage origins; sessionStorage и ещё не открытые origins могут потребовать повторного входа. Полного переноса профиля Chromium нет.

После запуска браузерного хоста:

```sh
node dist/index.js browser setup --shared-url http://127.0.0.1:4330 --cdp-env "" --executable-env ""
node dist/index.js browser diagnose
node dist/index.js run
```

`setup` автоматически записывает в исключённый из Git `.env` только путь к локальному токену. Команды требуют существующего разрешения `browser`/`browser_share`; setup добавляет их, сохраняя остальные. `diagnose` использует отдельный временный удалённый контекст и не читает пользовательские вкладки. У OSS 151 известен нативный дефект прозрачного Canvas: отчёт остаётся `passed: false`, команда возвращает код 1, но запуск host/агента не блокируется. Это предупреждение о корректности движка, не требование активации; JS-маскировка не применяется. Для возврата к отдельным браузерам: остановите агент, выполните `browser setup --shared-url ""`, запустите агент. Сохранённые старые профили остаются на месте; новые изменения shared-сессий обратно в них не импортируются.

## Агенты в отдельных контейнерах

На браузерном хосте выберите интерфейс, доступный из приватной Docker-сети. Например, на Linux при адресе bridge `172.17.0.1`:

```sh
node dist/index.js browser host --foreground --bind 172.17.0.1 --port 4330
```

Подставьте фактический адрес вашей приватной сети. В контейнере используйте этот адрес или `host.docker.internal` с Docker `--add-host=host.docker.internal:host-gateway`. На Docker Desktop поведение доступа к loopback зависит от сетевых настроек; проверьте доступ с контейнера. Не публикуйте 4330 в интернет и не добавляйте его в туннель телефона. Для другого физического сервера нужны приватная сеть либо доверенный HTTPS-прокси с поддержкой WebSocket Upgrade; HTTP допустим на изолированной доверенной сети.

В каждом агентском контейнере:

1. Установите те же зависимости проекта: SDK версии **1.63.0** и нативный **agent-browser 0.27.0** для платформы контейнера. Браузер и Docker внутри агента не устанавливайте. CLI agent-browser выполняет навигацию, snapshot/read/wait/screenshot и ввод; SDK остаётся транспортом к общему хосту и обслуживает persistence/пульт.
2. Смонтируйте предоставленный токен read-only, с владельцем процесса агента и правами 600. Задайте `ALIVE_BROWSER_SHARED_TOKEN_FILE=/run/alive/browser-token`. Секрет не должен попадать в образ или Git. Альтернатива — переменная `ALIVE_BROWSER_SHARED_TOKEN`, переданная средством управления секретами.
3. Настройте `modules.browser.engine: "fortress"`, `driver: "patchright"`, `enabled: true`, `headless: true`, `sharedUrl: "http://host.docker.internal:4330"`, пустые `cdpEndpointEnv` и `executablePathEnv`. Можно использовать `browser setup --engine fortress --shared-url ... --cdp-env "" --executable-env ""` при уже подключённом токене.
4. Используйте отдельный state directory/volume на агент. Его Telegram token, пользователи и `publicUrl` остаются его собственными настройками. Разные боты/контейнеры не должны одновременно опрашивать один Telegram token.

Клиент проверяет выбранный движок, digest OSS-образа и ожидаемую signing policy. При несовпадении или недоступном хосте он выдаёт ошибку; отдельный Chrome/Fortress автоматически не запускается. Лицензия/активация Fortress не требуются. Только опциональный приватный ключ Web Bot Auth хранится на браузерном хосте. Подпись устанавливается один раз глобально; один сервис имеет одну identity/origin policy.

## Жизненный цикл и ограничения

По умолчанию допускается восемь подключений, один контекст и восемь страниц на подключение. При превышении запрос отклоняется. Предел Fortress в 3 GiB RAM, два CPU и 512 процессов применяется к одному общему контейнеру. Активные вкладки всё равно расходуют память/CPU; число восемь является пределом подключений, а не гарантией производительности при любой нагрузке.

Состояние контекста сохраняется в приватный `shared-storage.json` каждые 15 секунд и при штатном закрытии. При аварии теряются изменения после последнего успешного сохранения. History, cache и sessionStorage не переносятся. Обрыв соединения удаляет только контекст этого агента. Перезапуск/падение общего движка отключает всех; клиенты отзывают пульты и при следующем подключении восстанавливают сохранённое состояние. Пользователь может потребоваться для повторного входа.

Все контексты разделяют движок, нативную идентичность и выходную сеть. Это сервис для доверенных агентов проекта, а не граница OS-изоляции для враждебных арендаторов. Сайт по-прежнему самостоятельно решает, разрешать ли доступ.

Сервис не выдаёт raw CDP движка. В процессе агента создаётся приватный loopback CDP-адаптер только для его daemon agent-browser: синтетические Target/session ID соответствуют страницам одного SDK-контекста, команды идут по авторизованному SDK-протоколу. Хост независимо проверяет точный allowlist page-scoped команд. Snapshot возвращает нативные ссылки `@eN`, пригодные для click/fill. Daemon использует отдельные временные HOME/socket directory без пользовательских config/provider/profile; при закрытии/отмене его соединение отзывается, локальный браузер не запускается. Произвольный CLI argv, глобальные операции с cookies и настройки браузера, а также вложенное/OOPIF Target attachment не поддерживаются. `request` остаётся отдельным подписанным read-only API-клиентом, а телефонный пульт работает с теми же вкладками. В dedicated-режиме (`sharedUrl: ""`) прежняя SDK-реализация остаётся без изменений.

`status` неоткрытого разговора не создаёт сессию и не занимает лимит. Неуспешный запуск освобождает пустую сессию роутера, поэтому сбой хоста не исчерпывает лимит навсегда. Протокольный шлюз запрещает глобальный CDP/закрытие движка, запуск вспомогательных браузеров, tracing, загрузку файлов с хоста и скачивания. Навигация ограничена HTTP(S)/about:blank; разрешены scoped-захват/ввод и GET/HEAD API-запросы в контексте. Приватные параметры никогда не добавляются к URL. Обновление внутреннего SDK-адаптера требует совместного обновления обеих закреплённых библиотек и E2E-проверки.

```sh
pnpm test:browser:shared
pnpm test:browser:oss
pnpm test:browser:fortress:e2e
ALIVE_BROWSER_TEST_FORTRESS=1 pnpm test:browser:shared:cli
# HTTPS fixture для этого варианта использует bridge Linux Docker:
ALIVE_BROWSER_TEST_FORTRESS=1 pnpm test:browser:shared:signing
ALIVE_BROWSER_TEST_FORTRESS=1 pnpm test:browser:agent:e2e
# Дополнительно нужен docker pull node:22-bookworm-slim:
ALIVE_BROWSER_TEST_FORTRESS=1 ALIVE_BROWSER_TEST_DOCKER_CLIENT=1 pnpm test:browser:agent:e2e
# Только тестовый браузер, имитирующий телефон, требует локального Chromium:
pnpm exec playwright install chromium
ALIVE_BROWSER_TEST_CHANNEL=chromium ALIVE_BROWSER_TEST_SHARED=1 ALIVE_BROWSER_TEST_FORTRESS=1 pnpm test:browser:router:e2e
```

Тесты используют локальные страницы и тестовый Bot API, не отправляют реальные Telegram-сообщения. Дополнительный старый SDK-тест `ALIVE_BROWSER_TEST_DOCKER_CLIENT=1 pnpm test:browser:shared:e2e` использует Python из установленного Fortress-образа с заменённым entrypoint и по умолчанию требует локальный Chrome для хоста fixture; браузер внутри Python-клиента не запускается. Для этой проверки синтетический временный хост слушает все интерфейсы на случайном порту; рабочая служба остаётся приватной. Последняя проверка использует один реальный OSS Fortress-контейнер и два независимых контроллера, без активации. `test:browser:agent:e2e` с Docker-флагом запускает **настоящий native agent-browser в отдельном Node-контейнере без установленного браузера**, проверяет refs/ввод/скриншот через общий Fortress, отсутствие browser-процесса в клиенте и очистку его удалённого контекста. Для Docker-проверок временный fixture-host слушает все интерфейсы на случайном порту; это не конфигурация рабочей службы.

Штатная остановка хоста: `node dist/index.js browser host-stop`. Обычный `alive stop` останавливает только агент и оставляет общий сервис доступным остальным.
