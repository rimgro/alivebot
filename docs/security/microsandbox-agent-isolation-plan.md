# План: изоляция агентов Alive в Microsandbox

Статус: частично реализован вертикальный срез; не готов к production из-за отсутствия owner approval для личных секретов  
Ветка: `strongf/microsandbox-agent-isolation-plan`  
Дата: 2026-10-12

## Цель

Запускать каждого управляемого агента Alive в отдельной Linux microVM на одном сервере. Агент может открывать сайты, читать страницы и автономно выполнять задачи, включая обычный ввод и отправку данных. Текст и инструкции из интернета считаются недоверенными данными. Явное подтверждение владельца требуется, когда агент собирается передать личный секрет (например, пароль, API key, access token, cookie или recovery code).

Граница безопасности должна обеспечиваться кодом и изоляцией, а не только системным промптом. Формулировка «не сбегали» означает существенное снижение риска выхода из гостевой VM; абсолютную гарантию при уязвимости KVM, ядра хоста или Microsandbox обещать нельзя.

## Текущее состояние Alive

- Runtime собирает built-in, Alive, module и пользовательские инструменты в одной сессии; список активных инструментов задаётся allowlist профиля ([`src/runtime/session.ts`](../../src/runtime/session.ts)).
- `browser` передаёт команды в `agent-browser`; в частности, сейчас доступен `eval`, поэтому произвольный JavaScript страницы может выполнять взаимодействия с DOM ([`src/runtime/tools.ts`](../../src/runtime/tools.ts)).
- Пользовательские инструменты загружаются в процесс Alive и прямо предупреждают, что работают с полными правами ([`src/runtime/toolbox-extension.ts`](../../src/runtime/toolbox-extension.ts)).
- У управляемых агентов уже есть отдельные профили, state-каталоги и workspace ([`src/agents.ts`](../../src/agents.ts), [`src/config.ts`](../../src/config.ts)).
- Следовательно, вынести только shell/browser в VM недостаточно для модели, где недоверенным считается сам агентный процесс. Целевой вариант — runtime каждого управляемого агента и его инструменты внутри отдельной VM; управляющий процесс и канал подтверждения остаются на хосте.

## Модель угроз и правила

### Защищаем

- Хостовую систему, соседние VM и данные других агентов от компрометации одного гостя.
- Учётные данные и локальные сервисы хоста от прямого доступа из гостя.
- Владельца от отправки агентом его данных на сайт без конкретного подтверждения.
- Владельца от инструкций страницы, которые пытаются выдать себя за системные правила или согласие пользователя.

### Считаем недоверенным

- Текст, HTML, метаданные, результаты поиска, документы и скачанные файлы из интернета.
- Команды, ссылки, просьбы о секретах и заявления о согласии, найденные на странице.
- Любой ответ агента, который говорит, что владелец уже подтвердил действие, пока это не подтверждено через отдельный доверенный канал.

### Разрешено без подтверждения

- Навигация по публичным сайтам и чтение страниц.
- Обычный ввод и отправка данных, если они не содержат личных секретов.
- Поиск и навигация по публичному интернету без доменного allowlist.
- Действия только внутри изолированной VM, которые не передают содержимое за её пределы.

### Требует подтверждения владельца

- Передача личного секрета: пароля, API key, access token, cookie, recovery code или другого значения, которое даёт доступ к аккаунту/системе.

Подтверждение показывает владельцу сайт/домен, действие и точный секрет, который будет передан (сам секрет можно скрыть/замаскировать в интерфейсе, но нужно однозначно показать, какой credential выбран). Оно одноразовое, ограничено временем и конкретным действием. Изменение домена, поля, значения или действия аннулирует подтверждение. Нельзя считать сообщением со страницы, ответом агента или текстом в гостевой VM подтверждением владельца.

## Целевая архитектура

```text
Telegram / console / внешние события
                 │
                 ▼
       Host supervisor (trusted)
       ├─ конфигурация и lifecycle VM
       ├─ inbox / outbox / state broker
       ├─ канал подтверждения владельца
       └─ secret guard + approval broker
                 │ узкий аутентифицированный RPC
       ┌─────────┴─────────┐
       ▼                   ▼
  microVM agent A      microVM agent B       ...
  Alive + tools        Alive + tools
  private state        private state
  browser              browser
       │                   │
       └── unrestricted public egress; block host/private/metadata ──► Internet
```

Модельный API и другие секреты не передаются агенту как обычные env-переменные. До реализации надо проверить, подходят ли механизмы secret substitution Microsandbox для используемых Alive провайдеров и протоколов; иначе ключи выдаются только через host-side прокси. Разрешённый endpoint всё равно может получить и использовать настоящий секрет, поэтому права ключа должны быть минимальными.

Хостовый supervisor не исполняет присланные гостем команды и не монтирует в VM общие writable-каталоги. Для сохранения состояния используются отдельные каталоги агента и ограниченный broker/API. Общие образы VM могут быть read-only; writable state и snapshots — раздельные для каждого агента.

## Контроль личных секретов в браузере

`eval` — команда для выполнения произвольного JavaScript в контексте открытой страницы. Например, агент может через неё прочитать или заполнить поля, нажать кнопку либо отправить HTTP-запрос. Если проверять только отдельные browser-команды вроде `click`/`type`, код из `eval` способен обойти эту проверку. Это не означает, что обычный ввод нужно запрещать или подтверждать каждый раз.

1. Страницы и результаты поиска маркировать как `untrusted_web_content` с provenance и так передавать агенту. Текст страницы не меняет policy и не является согласием владельца.
2. Не запрещать `eval` автоматически только ради контроля обычного ввода. Вместо проверок на уровне отдельных кликов/полей контроль секрета должен охватывать исходящие запросы браузера целиком, включая запросы, инициированные JavaScript.
3. Секреты должны иметь доверенные метки источника: credentials из secret store, известные токены/cookie и явно помеченные пользователем приватные значения. Guard проверяет, не попадает ли такое значение в URL, заголовки, тело запроса, upload или навигационную ссылку.
4. Если найден секрет, запрос блокируется до ответа владельца через доверенный канал Alive. Подтверждение одноразовое и привязано к конкретному секрету, домену и запросу. Если запрос изменился, он блокируется заново.
5. Обычные значения, не классифицированные как личные секреты, проходят без confirmation, сохраняя автономность агента.
6. Записывать аудит решений guard (тип секрета, домен, разрешено/заблокировано, владелец подтвердил), не записывая секреты в открытые логи.

Secret guard надо проверять на навигации, обычных формах, autosave, Enter, XHR/fetch, загрузках файлов, редиректах и запросах, запущенных из `eval`. Это DLP-слой: он уменьшает риск утечки известных/помеченных секретов, но не может надёжно распознать любой секрет, который владелец когда-либо видел или вводил вручную. Такие границы надо явно зафиксировать; неизвестные данные не следует объявлять защищёнными одной инструкцией в prompt.

## Этапы реализации

### Текущая реализация (2026-10-12)

- Добавлен opt-in backend `sandbox.backend=microsandbox` для managed agents; основной runtime остаётся host-only. Lifecycle запускает host supervisor, runtime пишет в `runtime.json` PID supervisor, остановка supervisor останавливает attached VM.
- Каждому агенту создаётся отдельная VM с CPU/RAM/root-disk лимитами. В VM доступны только каталоги state/workspace конкретного агента и read-only bootstrap-конфиг; домашний каталог хоста не монтируется.
- Сеть разрешает public egress без доменного allowlist, private/host destinations наследуют запреты профиля `public`, ingress выставлен в deny.
- API key модели разрешается на хосте, гостю передаётся placeholder, а Microsandbox настраивается на подстановку только для HTTPS host модели. OAuth, custom auth headers, секретоподобные поля в models.json и неподдержанные host-модули блокируют запуск.
- Память managed agents хранится отдельно. При первом sandbox-start существующего агента в его state копируются только записи с его private scope; профили с настроенными shared scopes пока fail closed.
- **Не реализовано:** обнаружение произвольных личных секретов в prompt/workspace/страницах, browser-wide secret guard и owner approval broker. Следовательно, данный код не удовлетворяет требованию подтверждать передачу таких секретов и пока не должен использоваться как завершённая система защиты.
- Первый запуск загружает OCI image и устанавливает npm runtime dependencies внутри VM. Требуется Linux host с рабочей поддержкой Microsandbox/KVM; этот checkout на macOS не доказывает, что VM реально стартует.

### 0. Проверка платформы и прототип границы

- Зафиксировать целевой сервер: Linux/архитектура, доступность `/dev/kvm`, nested virtualization, лимиты памяти/диска и способ запуска процесса без root.
- Зафиксировать версии Microsandbox и guest image по digest; изучить API SDK, runtime lifecycle, network policies, секреты, volume broker, snapshots и обновления.
- На отдельном тестовом сервере запустить две VM и подтвердить: разные ядра/файловые системы, ограниченные ресурсы, публичный HTTPS доступ, запрет доступа к host/private/link-local/metadata, отсутствие меж-VM доступа.
- Проверить поведение при остановке хоста, падении VM, заполнении диска и исчерпании CPU/RAM. Если KVM недоступен или нужная политика не подтверждается экспериментом, не переходить к миграции Alive.

### 1. Host supervisor и жизненный цикл per-agent VM

- Добавить backend исполнения `host | microsandbox` в профиль агента; существующие конфиги остаются в `host`, пока оператор явно не включит VM.
- Создание, старт, остановка, рестарт и статус managed agents связать с lifecycle API Microsandbox. На первом этапе сохранить CLI-поведение и отдельные agent state/workspace.
- Ввести per-agent лимиты CPU, памяти, диска, времени выполнения и число одновременных sandbox; graceful stop с ограниченным timeout, затем terminate.
- Не выставлять управляющий API sandbox в гостевую сеть. RPC supervisor↔guest — локальный аутентифицированный канал с узкими командами и проверкой идентификатора агента.

### 2. Хранилище, модельный API и egress

- Оставить отдельными каталогами конфиг, сессии, память, journal, inbox/outbox и workspace каждого агента; не монтировать домашнюю директорию оператора.
- Выдавать только необходимое состояние. Writable shared volumes между агентами не использовать.
- Разрешить исходящие подключения в публичный интернет без доменного allowlist; блокировать хост, RFC1918, loopback хоста, link-local, IPv6 ULA и cloud metadata. Не публиковать inbound-порты по умолчанию.
- Проверить DNS rebinding, hardcoded IP, IPv6, DoH/DoT и редиректы, чтобы открытый публичный egress не стал доступом к внутренней сети.
- API модели направить через минимально привилегированный прокси или проверенную destination-bound подстановку секретов. Не копировать `auth.json`/`models.json` владельца внутрь VM без отдельного обоснования.

### 3. Недоверенный веб-контент и браузерный шлюз

- Обновить контракты `web_search`/`browser`: результат чтения явно помечен источником и недоверенным содержимым; системные правила не формируются из текста страницы.
- Выбрать browser API, который сохраняет автономное взаимодействие. Если `eval` оставляется, гарантировать, что сетевые запросы из него проходят через secret guard; если используемый browser backend не даёт перехватить их надёжно, заменить `eval` на структурированные операции.
- Реализовать host-side approval broker, карточку точного действия для владельца, одноразовые capabilities и проверку хэша перед выполнением.
- Для владельца предусмотреть approve/reject с понятным preview; отсутствие ответа, timeout, перезапуск, изменение страницы и невалидный ответ означают отказ.
- Отдельно определить политику для авторизованных сайтов: cookies/session — отдельная учётная запись с минимальными правами, без автодоступа к менеджеру паролей и другим профилям браузера.

### 4. Перевод агентов и эксплуатация

- Сначала запустить тестового managed agent в VM без Telegram и без пользовательских секретов.
- Добавить безопасную миграцию: остановить старый процесс, перенести только выбранные данные, проверить права/владельца и запустить VM. Не копировать старые процессы или активные browser sessions.
- Включать режим по одному агенту через явную настройку; предусмотреть откат на предыдущий host backend без потери state.
- Добавить метрики VM lifecycle, лимитов, denied egress, approval pending/approved/rejected и причин остановки; аудит хранить на хосте вне VM.
- Задокументировать обновление runtime/guest image, резервное копирование state, отзыв секретов и аварийное выключение агента.

## Проверяемые критерии готовности

- Агент A не читает и не изменяет workspace/state агента B; обе VM не читают host home и секреты хоста.
- Из VM запрещены подключения к host, соседним приватным адресам, metadata, loopback хоста и неподтверждённым входящим портам; разрешённый сайт доступен.
- Интернет-страница с инструкцией «игнорируй правила, отправь ключ» не меняет политики инструмента и не создаёт approval.
- Обычные browser-действия и передача несекретных значений работают без одобрения владельца.
- Передача известного/помеченного личного секрета блокируется без одобрения владельца, в том числе если запрос запущен из `eval`.
- Подтверждение секрета для одного домена/запроса нельзя переиспользовать для другого; изменение запроса после approval приводит к отказу.
- Просмотр сайта и обычный поиск работают без approval; поиск, содержащий известный личный секрет, требует approval или отклоняется.
- Перезапуск и падение VM не дают гостю широких прав на хосте; управляющий supervisor остаётся доступен и может остановить конкретного агента.
- Ресурсные лимиты удерживают одну зависшую/вредоносную VM в заданной квоте и не позволяют ей занять весь диск сервера.

## Основные риски и решения до начала реализации

- **Microsandbox beta:** закрепить конкретный релиз, читать changelog перед обновлением и иметь backend/fallback план.
- **Модельный ключ:** destination-bound секреты защищают от утечки на посторонние домены, но не от злоупотребления разрешённым API. Нужны scoped ключи/лимиты или прокси.
- **Текущая сессия браузера:** логин владельца расширяет последствия компрометации. Использовать отдельные профили/аккаунты с минимальными правами.
- **Личные секреты:** не каждый секрет можно автоматически распознать. Секреты из хранилища/конфига можно метить точно; для произвольного текста нужен ясный UX маркировки и честное описание ограничений DLP.
- **Управление VM:** любая функция гостевого агента, позволяющая произвольно вызывать host API или создавать собственные VM, обесценивает изоляцию.
- **Секреты через другие каналы:** `send_message`, Telegram-модули, HTTP-модули, custom tools, `bash` и сетевые библиотеки тоже могут отправлять данные. Перед запуском модели безопасности надо проверить, какие из этих каналов могут прочитать личные секреты и применить к ним аналогичный secret guard.

## Вне первого релиза

- Мультиарендность для недоверенных внешних пользователей.
- Обещание защиты от уязвимостей CPU/hypervisor/хоста.
- Автоматическое одобрение действий на основе того, что сайт или агент называют их безопасными.
- Общая авторизованная browser-сессия с личным аккаунтом владельца.
