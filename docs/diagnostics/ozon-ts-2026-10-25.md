# Ozon на `ts`: почему «Похоже, нет соединения / Выключите VPN» и как починено

Дата: 2026-10-25. Машина: `ts` (`AMELIA-PC`, Windows + WSL2), агенты `developer`, `slava-manager`, `sre_devops`.

## Итог (коротко)

- Браузер агентов — **Fortress в Docker на хосте (headless)**, как и было. Никакого внешнего CDP/Windows-Chrome не осталось.
- Навигация на `ozon.ru` теперь стабильно даёт **капчу** (её можно пройти), а не плашку «нет сети / выключите VPN».
- Капча проверена на прохождение: `POST /abt/captcha/result` → `200`, после неё грузится настоящая главная Ozon (каталог), плашки нет.

## Что вызывало плашку

`Похоже, нет соединения / Выключите VPN` — это не проблема сети, а страница антибота Ozon
(`ozon-antibot: 1`). Возникала в двух случаях:

1. **Пока персона браузера не совпадала с выходным IP.** Fortress-контейнер стартовал с
   гео-детектом через прокси: `--uxr-country=DE`, `--uxr-timezone=Europe/Berlin`,
   `--uxr-languages=en-US,en`, а `navigator.userAgent` был `macOS` при `navigator.platform=Win32`.
   Плюс **WebRTC отдавал немецкий IP** `153.52.66.88` (`vpn2`) при HTTP-IP `195.64.156.206` (Сочи).
   Ozon это читает как «VPN» и отдаёт именно эту плашку.
2. **После неудачной попытки решить капчу.** `POST /abt/captcha/result` → `403 {"ok":false,"retryable":true}`,
   и Ozon на следующем документе отдаёт страницу-отказ (`fab_cp_…`). Перезагрузка возвращает капчу.

## Что сделано (всё на `ts`)

1. **Персона RU и отсутствие утечки WebRTC** (из исходников + systemd, см. «Где что лежит»):
   - `--uxr-country=RU --uxr-timezone=Europe/Moscow --uxr-languages=ru-RU,ru`;
   - `--uxr-webrtc-policy=disable_non_proxied_udp` — WebRTC больше не светит немецкий IP;
   - гео-детект лаунчера (`ipapi.co`/`ipinfo.io`) идёт direct и видит RU.
   Проверка в контейнере: `tz=Europe/Moscow`, `lang=ru-RU`, `platform=Win32`, `UA=Windows`,
   `WEBRTC=[]`, HTTP-IP `195.64.156.206`.
2. **mihomo (`/etc/mihomo/config.yaml`)**: включён `sniffer` (`parse-pure-ip`, `override-destination`) —
   доменные правила наконец применяются к трафику контейнера; `ozon.ru/ozone.ru/ozonusercontent.com/ozon.by/ozon.kz/ozon.com`
   и гео-сервисы → `DIRECT`. Бэкапы: `config.yaml.bak-*`.
3. **Откат Windows-CDP** (эксперимент с настоящим Chrome убран полностью):
   удалены `alive-win-cdp-tunnel.service`, `alive-win-chrome-ensure.{service,timer}`,
   `alive-cdp-chrome.cmd` из Startup, `chrome.exe` остановлен; `host.json` и
   `shared-server.js` восстановлены из бэкапов (`cdpEndpointEnv: ""`, `engine: fortress`).

## DNS для доменов, заблокированных в РФ

Контейнер резолвил через резолвер хоста (ISP-фильтрация), поэтому `linkedin.com`, `web.whatsapp.com`
не открывались вообще (`ERR_NAME_NOT_RESOLVED`), хотя через VPN доступны. Сделано:

- mihomo слушает DNS на docker-бридже: `dns.listen: 172.17.0.1:53` (было `127.0.0.1:1053`);
  drop-in `mihomo.service.d/docker-dns.conf` (`After/Wants=docker.service`, `Restart=always`), чтобы
  адрес бриджа существовал к моменту старта.
- запуск контейнера получает `--dns` из env `ALIVE_FORTRESS_DNS` (реализовано в исходниках,
  `src/modules/browser/fortress.ts`), значение задано в `alive-browser-host.service.d/dns.conf`.
- Итог: в контейнере `nameserver 172.17.0.1`, ответы — fake-ip `198.18.0.x`, дальше mihomo по правилам
  (`ozon.ru` → DIRECT, остальное → PROXY). Проверено: LinkedIn `200`, WhatsApp Web `200`, Ozon — капча.

## Проверка

- 4 «свежих» сессии подряд: `307 → 403 (?__rr=1)` и страница капчи, **плашки нет ни разу**.
- Решение капчи «человеческой» траекторией: `200` на `/abt/captcha/result`, далее заголовок
  «Ozon маркетплейс – миллионы товаров по выгодным ценам» и каталог в тексте.
- `alive browser doctor --online`: `Shared browser host: http://127.0.0.1:4330; reachable; 151.0.7908.0`.
- Состояние хоста: `engine=fortress`, `browserVersion=151.0.7908.0`, `ready=true`.

## Где что лежит / как откатывать

| Что | Где | Бэкап |
| --- | --- | --- |
| резолвер и WebRTC-политика | env `ALIVE_FORTRESS_DNS` / `ALIVE_FORTRESS_WEBRTC_POLICY` в `alive-browser-host.service.d/*.conf` | удалить |
| персона через env | `/etc/systemd/system/alive-browser-host.service.d/persona.conf` | удалить |
| маршрутизация | `/etc/mihomo/config.yaml` | `config.yaml.bak-*` (проверка: `mihomo -t -d /etc/mihomo`) |
| конфиг хоста | `/etc/alive-browser/host.json` | `host.json.bak-*` |

Поведение реализовано в репозитории (`src/modules/browser/fortress.ts`, коммит `6cf834f`):
`TILION_LANG` проходит вместе с остальными локаль-переопределениями, `ALIVE_FORTRESS_DNS` добавляет
`--dns`, `ALIVE_FORTRESS_WEBRTC_POLICY` — `--uxr-webrtc-policy`. Обе переменные по умолчанию пусты,
то есть без них запуск контейнера не меняется. Развёрнутый `/opt/alive-browser/dist` собран из этого
коммита (сверено по `md5sum` нетронутых файлов с `/home/rimgro/Projects/alive/dist`).

## Осталось (по желанию)

Модуль браузера не распознаёт капчу/отказ Ozon как проверку: `challengeKind()` знает Cloudflare/
Yandex-виджеты и заголовки «Проверяем браузер»/«Проверка на бота», но не Ozon. Из-за этого агент
считает страницу капчи обычным контентом и может сам дёргать слайдер — каждая неудачная попытка
даёт ту самую плашку «нет сети». Патч: добавить в `challengeKind()` селектор виджета Ozon
(`img.puzzle` / `abt-challenge`), а заголовок «Antibot Captcha» и текст «Похоже, нет соединения» →
`verification`/`denied` с handoff оператору. Требует пересборки `dist` и перезапуска агентов.

Отпечаток в контейнере: `tz=Europe/Moscow`, `lang=ru-RU`, `platform=Win32`, `UA=Windows`, `userAgentData=Windows`,
`WEBRTC=[]`. Персона стабильна между перезапусками (один раз наблюдался транзиентный `UA=macOS` сразу после
старта контейнера — на следующем старте не воспроизвёлся; если повторится, перезапустить `alive-browser-host`).

fake-ip в контейнере кэшируется, после рестарта mihomo старые IP невалидны (Chrome сам сбрасывает кэш за ~минуту).
