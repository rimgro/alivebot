# Telegram

Полноценная интеграция с Telegram Bot API: бот **принимает** сообщения, **отправляет**
ответы агента, **читает историю чатов** и имеет инструмент для всего остального
(участники, реакции, пины, форварды, файлы).

Реализация: [`src/modules/telegram/`](./src/modules/telegram/).
Контракт, на котором она построена: [EVENTS_API.md](./EVENTS_API.md).

## 1. Настройка за 3 шага

1. Создайте бота у [@BotFather](https://t.me/BotFather) и получите токен.
2. Положите токен в окружение (в конфиг лучше не коммитить):

   ```bash
   export ALIVE_TELEGRAM_TOKEN="123456:ABC-DEF..."
   ```

3. Включите модуль в `alive.config.json`:

   ```json
   "modules": {
     "telegram": { "enabled": true, "tokenEnv": "ALIVE_TELEGRAM_TOKEN" }
   }
   ```

   Либо положите токен в gitignored `alive.config.local.json` (работает без env):

   ```json
   { "modules": { "telegram": { "enabled": true, "token": "123456:ABC-DEF…" } } }
   ```

Проверка без запуска агента:

```bash
alive telegram me                       # кто я: имя, @username, id
alive telegram chat @some_channel       # getChat по @username или id
alive telegram send 123456789 "привет"  # отправить сообщение
alive telegram chats                    # что уже записано локально
```

Для приватного чата пользователь должен сначала написать боту сам (или нажать
`/start`) — Bot API не позволяет писать первым произвольному пользователю.
В группах бот должен состоять в чате; privacy mode влияет на то, какие обычные
сообщения он получает. Для Bot-to-Bot Communication включи соответствующий режим
у BotFather. Сам Alive дополнительно принимает bot-authored сообщения только от
ID в `allowedBotIds` и только при явном упоминании/ответе этому боту; это
ограничение защищает от случайных ботов и бесконечных цепочек ответов.

## 2. Конфиг

```json
"modules": {
  "telegram": {
    "enabled": true,
    "token": "",
    "tokenEnv": "ALIVE_TELEGRAM_TOKEN",
    "managedBotTtlMs": 720000,
    "apiBase": "https://api.telegram.org",
    "allowedChatIds": [],
    "allowedUserIds": [],
    "allowedBotIds": [],
    "pollTimeoutSec": 25,
    "allowedUpdates": ["message", "edited_message", "channel_post", "edited_channel_post", "callback_query"],
    "parseMode": "",
    "linkPreview": true,
    "allowUrlButtonsInGroups": false,
    "typingIndicator": true,
    "ackReaction": "",
    "ingestEdits": true,
    "editDebounceMs": 3000,
    "editExpectsReply": false,
    "historyLimitPerThread": 0,
    "maxMessageChars": 4000,
    "transcription": {
      "enabled": true,
      "apiKeyEnv": "GROQ_API_KEY",
      "model": "whisper-large-v3-turbo",
      "maxBytes": 20971520,
      "timeoutMs": 30000
    },
    "transcriptionRetries": 2,
    "transcriptionRetryDelayMs": 1500
  }
}
```

| Поле | Смысл |
|---|---|
| `token` / `tokenEnv` | токен; переменная окружения приоритетнее файла |
| `managedBotTtlMs` | сколько ждёт подтверждение Managed Bot; 10–15 минут, по умолчанию 12 (`720000` мс) |
| `apiBase` | базовый URL Bot API (для локального bot-api server) |
| `allowedChatIds` | белый список chat id; пусто = все чаты бота |
| `allowedUserIds` | белый список user id; пусто = все пользователи |
| `allowedBotIds` | явный список trusted peer-bot IDs; сообщения принимаются только в группах и только если адресованы этому боту упоминанием/ответом |
| `pollTimeoutSec` | long-poll таймаут `getUpdates` |
| `allowedUpdates` | какие типы апдейтов подписывать |
| `parseMode` | `""` (plain), `"HTML"` или `"MarkdownV2"`; при ошибке разметки сообщение уходит plain-текстом |
| `linkPreview` | показывать превью ссылок |
| `allowUrlButtonsInGroups` | `true` разрешает агенту ставить `url`-кнопки в группы/каналы; по умолчанию `false` |
| `typingIndicator` | слать `typing…`, пока агент работает над ответом |
| `ackReaction` | эмодзи-реакция на входящее сообщение как подтверждение (пусто = выкл) |
| `ingestEdits` | приносить ли редактирования сообщений |
| `editDebounceMs` | окно склейки правок одного сообщения, мс (по умолчанию 3000; `0` = без склейки) |
| `editExpectsReply` | `true` — правка снова обязывает ответить по общим правилам; по умолчанию `false` (правка ждёт ответа только при явном обращении) |
| `historyLimitPerThread` | хранить не больше N сообщений на чат (0 = без лимита) |
| `maxMessageChars` | размер части при разбиении длинных ответов (Telegram лимит — 4096) |
| `transcription.enabled` | распознавать ли входящие голосовые (`false` = только пометка о вложении) |
| `transcription.apiKeyEnv` | имя переменной окружения с ключом провайдера; пусто = выкл |
| `transcription.model` | модель распознавания (OpenAI-совместимый эндпоинт Groq) |
| `transcription.maxBytes` | максимум на одно голосовое; больше — не скачивается и не отправляется |
| `transcription.timeoutMs` | бюджет одной попытки: скачивание + запрос к провайдеру |
| `transcriptionRetries` | сколько раз повторить распознавание после **временной** ошибки; `0`–`2`, по умолчанию `2` (не больше трёх попыток на голосовое) |
| `transcriptionRetryDelayMs` | базовая пауза экспоненциального backoff между попытками, мс; `10`–`60000`, по умолчанию `1500` |

## 3. Как это работает

### Треды

Тред — канонический ключ диалога во всём рантайме (enforcement ответов,
правила уведомлений, маршрутизация исходящих). Формат:

```
telegram:<chatId>              обычный чат (личный, группа, супергруппа, канал)
telegram:<chatId>/<topicId>    тема в форуме (message_thread_id)
```

`chatId` отрицательный для групп/каналов (`-100…`), поэтому разделитель темы — `/`.

### Входящие

Модуль держит long polling `getUpdates` с durable-offset (`.alive/modules/telegram/state.json`),
поэтому после перезапуска старые апдейты не переигрываются. Каждый апдейт:

- фильтруется (свои сообщения игнорируются; bot-authored сообщения принимаются только от `allowedBotIds` и только при явном упоминании/ответе этому боту; user allowlist проверяется отдельно);
- превращается в `user_message` в durable-инбоксе с `dedupeKey`
  `telegram:msg:<chatId>:<messageId>` — повторная доставка не создаст дубль;
- записывается в общую историю (`history`), с `meta.eventId`, чтобы `reply_to`
  агента можно было превратить в Telegram `reply_to_message_id`;
- обновляет каталог чатов (заголовок, тип, @username, тема последнего сообщения).

Что попадает в текст события: текст или подпись, цитата сообщения, на которое
ответили, метка форварда, список вложений (фото/документ/голос/видео/стикер/
локация/контакт/опрос), пометка «edited», а для фото — путь к автоматически
сохранённому файлу (см. ниже). В `payload` — структурированные
`chat`, `author`, `messageId`, `topicId`, `attachments`, `image`.

`expectsReply` (агент обязан ответить или закрыть тред):

- личный чат — всегда;
- команда (`/start`), упоминание бота (`@bot`) или `text_mention` — да;
- реплай на сообщение бота — да;
- прочая болтовня в группе и посты каналов — нет (наблюдение, не долг).

#### Правки (`edited_message`, `edited_channel_post`)

Правка — это исправление, а не новый вопрос. Чтобы пять быстрых исправлений
не превращались в пять запусков и пять ответов (#113):

- правки одного `messageId` склеиваются в **одно** событие: каждое новое
  исправление перезапускает окно `editDebounceMs` (по умолчанию 3 с), событие
  уходит после паузы и несёт финальный текст, `meta.edits` (сколько правок
  вошло в пачку), `meta.firstEditAt` (время первой правки, мс) и прежнюю
  пометку «edited» в тексте; `editDebounceMs: 0` отключает склейку. В историю
  попадает одна запись с финальным текстом, промежуточные версии не хранятся;
- `expectsReply` для правки по умолчанию `false`; `true` только если новая
  версия явно адресована боту — упоминание `@bot`, `text_mention` или реплай
  на сообщение бота. Флаг `editExpectsReply: true` возвращает старое поведение
  (правка обязывает ответить по общим правилам);
- если агент уже ответил на исходное сообщение (в истории есть исходящее с
  `replyTo` = этот `messageId`), в текст события добавляется пометка
  «правка после ответа», а `expectsReply` остаётся `false`, пока правка не
  адресована боту явно; факт виден в `payload.editedAfterReply`. Это правило
  действует и при `editExpectsReply: true`: ответ уже дан, правка не создаёт
  нового обязательства;
- пока на этом треде активно работает запуск, правка не отправляется в инбокс
  сразу: она продолжает копиться в пачке и уходит один раз, когда запуск
  уходит в `idle` (рантайм однопоточный — параллельный запуск не появится,
  событие попадает в его же pending-батч); события правок помечаются
  `priority: "low"`, чтобы не конкурировать со свежими сообщениями людей;
- правка собственного сообщения бота отбрасывается по `botId`, как и обычное
  собственное сообщение.

Callback-кнопки (`callback_query`) приходят как `user_message` «[button pressed] …»,
и бот сразу отвечает на callback, чтобы у клиента не висел спиннер.

### Распознавание голосовых

Входящие voice notes распознаются через Groq Audio Transcriptions
(`modules.telegram.transcription.model`, по умолчанию `whisper-large-v3-turbo`) только когда
одновременно выполнено два условия: `transcription.enabled` не выключен и в окружении процесса
задан ключ из `transcription.apiKeyEnv` (по умолчанию `GROQ_API_KEY`). Двойное условие важно:
ключ, который вы экспортируете для другой фичи (например, эмбеддингов памяти), сам по себе
аудио никуда не отправляет.

Расшифровка добавляется к тексту события и к записи истории; исходное вложение и caption
сохраняются. В `payload.transcription` есть `provider`, `model`, `status` и `text`. `status` —
одно из `transcribed`, `failed`, `too_large`, `quota_exhausted`, `disabled`, `not_configured`.
В историю попадает только сам транскрипт: подсказки про настройку и разовые ошибки провайдера
остаются только в тексте события, чтобы не засорять поиск по истории.

Обрабатываются только voice notes; другие аудио (`audio`, документы) не отправляются.
Лимит размера (`transcription.maxBytes`, по умолчанию 20 MiB) проверяется по метаданным
и ещё раз в процессе потоковой загрузки — аудио целиком в память при превышении не читается.
Бюджет `transcription.timeoutMs` (по умолчанию 30 секунд) ограничивает одну попытку:
скачивание и запрос к провайдеру вместе. При выключенном распознавании, отсутствующем ключе,
превышении лимита или ошибке API сообщение не теряется: агент получает пометку, что
транскрипции нет.

Распознавание идёт синхронно в цикле long polling: пока голосовое скачивается и распознаётся,
следующие апдейты ждут. Если это мешает, уменьшите `timeoutMs`/`transcriptionRetries` или
выключите `transcription.enabled`.

#### Повторы, дневная квота и логи (#117)

Голосовое распознаётся с ограниченным числом попыток: `1 + transcriptionRetries` (по умолчанию
три; настройка допускает не больше двух повторов, то есть не больше трёх попыток) и только при
**временных** сбоях — таймаут, обрыв соединения/DNS, HTTP 5xx и 429 с коротким `retry-after`
(≤ 10 секунд). Пауза между попытками растёт экспоненциально от `transcriptionRetryDelayMs`
(×2, не больше 30 секунд) и размывается джиттером ±20%; если провайдер прислал `retry-after`,
используется его значение.

Никогда не повторяются: 401/403 (неверный ключ), исчерпанная квота (`rate_limit`/`daily`,
маркеры RPD/TPD, `insufficient_quota`), неподдерживаемый формат (остальные 4xx) и слишком
большой файл. Такая ошибка завершает распознавание с первой попытки.

Если провайдер ответил ошибкой **дневной** квоты, модуль пишет маркер в
`<stateDir>/modules/telegram/state.json` (`transcriptionQuota`) и до конца суток (UTC) больше
не отправляет голосовые в API: сообщения приходят как обычно, с пометкой, что транскрипции
нет (`payload.transcription.status = "quota_exhausted"`). Маркер снимается при смене дня или
при изменении настроек распознавания (ключ, модель, лимиты, повторы) — тогда следующее
голосовое снова пробует API.

Контракт логов: на одно голосовое — не больше одной строки `warn`
(`telegram voice transcription failed` с `attempts`, `class` и `reason`; для квоты —
`telegram voice transcription paused until the provider quota resets`). Детали каждой попытки
пишутся только на уровне `debug` (`telegram voice transcription attempt failed`). Ни ключ, ни
тело ответа провайдера, ни аудио в лог не попадают.

Ключ — секрет: задайте его в окружении хост-процесса (например, в gitignored `.env`), а не
в Telegram, tracked config или PR. `GROQ_API_KEY` читается при обработке каждого голосового,
поэтому после правки `.env` достаточно нового апдейта; но демон, запущенный без ключа,
подхватит его только после перезапуска процесса. Когда ключ задан, аудио передаётся Groq; учитывайте условия
хранения и обработки данных этого провайдера. Для локальных тестов реальный ключ не нужен:
запросы к Groq подменяются mock-ответом (`npm run test:modules`).

### Автоматическое сохранение фото

Входящее фото (самый крупный размер из `photo[]`) скачивается сразу при обработке
апдейта и кладётся в workspace по пути
`telegram-files/<messageId>-<fileUniqueId>.<ext>` (расширение берётся из mime-типа,
для фото Telegram по умолчанию `.jpg`). В текст события и в историю добавляется
строка `image saved: telegram-files/… (read this local file to see the image)`, а в
`payload.image` появляется `{ path, mime, bytes }`. Агент читает файл из workspace
напрямую, без отдельного вызова `telegram(action: "download_file", …)`; подсказка
про `download_file` в тексте события остаётся как fallback для остальных вложений.

Ограничения: сохраняется только `photo` (документы и картинки, отправленные
документом, не трогаются); не больше одного фото на сообщение; жёсткий лимит
10 MiB проверяется по метаданным и ещё раз при потоковой загрузке; таймаут
30 секунд покрывает `getFile` и скачивание; загрузка прерывается вместе с модулем.
При ошибке, превышении лимита или отсутствии `file_id` сообщение не теряется — в
событии появляется короткая строка `image not saved: …`, а в лог уходит только
причина (без содержимого, URL и токена). Разовые ошибки в историю не попадают,
чтобы не засорять поиск.

### Текст PDF

PDF-документы **не обрабатываются при поступлении**: входящий PDF остаётся обычным
вложением с именем и `file_id`. Сначала агент скачивает его:

```text
telegram(action="download_file", file_id="<из вложения>", name="report.pdf")
```

`download_file` возвращает локальный путь в `<workspace>/telegram-files/`. Затем текст
читается по требованию:

```text
telegram(action="pdf_text", path="<путь из download_file>", offset=0, limit=12000)
```

Так содержимое документа не попадает в контекст само по себе, а читается порциями:
`offset` — смещение в символах (по умолчанию 0), `limit` — размер порции (по умолчанию
12 000, максимум 40 000). В ответе есть короткий заголовок с `pages`, `totalChars`,
`offset` и `nextOffset`, когда текст продолжается.

Извлечение локальное: PDF не отправляется ни в один внешний сервис, `file_id` для
`pdf_text` не принимается. Лимиты: файл до 20 MiB, первые 50 страниц, не больше
40 000 символов текста, разбор ограничен примерно 20 секундами. При обрезке в тексте
остаётся явный маркер `[PDF text truncated: ...]`. Читать можно только `.pdf`-файлы
внутри каталога `telegram-files`; пути и симлинки за его пределы отклоняются.

### Исходящие

`send_message` в тред `telegram:…` попадает в модуль (он claimer этих тредов).
Дальше:

- текст разбивается по границам абзацев/строк/предложений на части
  ≤ `maxMessageChars`, каждая часть уходит отдельным `sendMessage`;
- `reply_to` агента резолвится: числовой message id, id записи истории
  (`telegram:42:1005`) или id события (`evt_…`) — последний ищется по `meta.eventId`
  в истории;
- ответ уходит в ту же тему форума (`message_thread_id`);
- при ошибке парсинга разметки сообщение автоматически переотправляется plain-текстом;
- всё отправленное пишется в историю как `outbound` с id `telegram:<chatId>:<messageId>`;
- `typing…` гасится, как только сообщение ушло.

### Вложения в исходящих

`send_message` умеет доставлять локальный файл из workspace: передайте
`attachment` — путь относительно workspace (например,
`telegram-files/42-photo.jpg`) — и при необходимости `attachment_kind`
(`photo` или `document`). Одно вложение на сообщение.

- Картинки (`image/*` по расширению) уходят как `sendPhoto`, остальные файлы —
  как `sendDocument`. `attachment_kind: "document"` заставляет отправить картинку
  файлом.
- Текст сообщения становится подписью (caption). Лимит подписи — 1024 символа;
  остаток автоматически уходит отдельным текстовым сообщением.
- Лимиты Telegram: фото ≤ 10 MiB, документ ≤ 50 MiB. Файл больше лимита
  отклоняется до первой отправки; для картинки > 10 MiB используйте
  `attachment_kind: "document"`.
- Путь обязан быть относительным и оставаться внутри workspace: `..`,
  абсолютные пути и симлинки, ведущие наружу, отклоняются. Проверяются
  существование и регулярность файла; для sandbox-профиля проверка существования
  происходит при чтении через workspace-мост.
- Вложение записывается в историю (`attachments` с `kind`, `name`, `mime`,
  `size`, `meta.path`); `reply_to` и тема форума продолжают работать.
- Обычные текстовые сообщения без `attachment` отправляются как раньше.

### Кнопки быстрого ответа

`send_message` принимает необязательный `buttons` — ряды inline-кнопок, по 1–3
кнопки в ряду. Каждая кнопка — либо callback-действие, либо ссылка:

```json
{
  "thread": "telegram:42",
  "text": "Подтвердить?",
  "buttons": [
    [{ "text": "Да", "data": "approve" }, { "text": "Нет", "data": "reject" }],
    [{ "text": "Документация", "url": "https://example.com/docs" }]
  ]
}
```

- `{ "text", "data" }` отправляет `callback_data`. Значение — 1–64 **байта**
  UTF-8 (кириллица занимает больше одного байта на символ). Слишком длинное
  значение отклоняется до отправки с ошибкой, в которой указаны кнопка и
  фактический размер; усечения нет.
- `{ "text", "url" }` открывает ссылку. В группах и каналах такие кнопки по
  умолчанию запрещены, чтобы агент не публиковал произвольные ссылки без
  разрешения. Включайте `modules.telegram.allowUrlButtonsInGroups: true` только
  для доверенных групп.
- Нажатие на callback-кнопку приходит тем же механизмом, что и раньше: событие
  `user_message` в том же треде, с автором и `payload.data`; модуль вызывает
  `answerCallbackQuery`, поэтому спиннер в клиенте останавливается.
- Inline-кнопки не занимают область над полем ввода и не «залипают» там.
- В истории (`meta.buttons`) сохраняются подписи, тип кнопки и размер
  callback-данных; сами значения `data` в логи не попадают.

### Индикатор набора

Пока агент работает над ответом, модуль раз в 4.5 секунды шлёт `sendChatAction: typing`
для треда. Индикатор жёстко ограничен по времени, поэтому упавший run не оставит
бота «печатающим» навсегда.

## 4. Инструмент `telegram`

Основной канал ответа — `send_message` (маршрутизируется сам). Инструмент
`telegram` нужен для всего остального:

| `action` | Что делает | Основные параметры |
|---|---|---|
| `me` | личность бота и статус модуля | — |
| `list_chats` | локальный каталог чатов с количеством сообщений | `limit` |
| `chat_info` | `getChat` + счётчик участников + локальная статистика | `chat` |
| `resolve_chat` | найти чат по `@username`, id или ссылке | `chat` |
| `history` | читать локальную историю (по умолчанию свежие сверху) | `chat`, `query`, `limit`, `before`, `after`, `since`, `until`, `direction`, `order` |
| `search` | поиск по всем Telegram-чатам | `query`, `limit` |
| `members` | администраторы + число участников | `chat` |
| `member` | статус участника | `chat`, `user_id` |
| `send` | отправить в произвольный чат/тему (проактивно) | `chat`, `text`, `reply_to`, `topic` |
| `edit` | отредактировать сообщение бота | `chat`, `message_id`, `text` |
| `delete` | удалить сообщение | `chat`, `message_id` |
| `forward` | переслать сообщение | `from_chat`, `to_chat`, `message_id`, `topic` |
| `react` | поставить реакцию | `chat`, `message_id`, `emoji` |
| `typing` | включить `typing…` | `chat`, `topic` |
| `pin` / `unpin` | закрепить/открепить | `chat`, `message_id` |
| `download_file` | скачать файл в workspace | `file_id`, `name` |
| `pdf_text` | прочитать текст скачанного PDF порциями | `path`, `offset`, `limit` |
| `set_commands` | зарегистрировать команды бота | `commands` |

`chat` везде принимает полный тред (`telegram:-100123/7`), голый id (`-100123`)
или `@username`. Скачанные файлы кладутся в
`<workspace>/telegram-files/<имя>` (лимит 25 МБ). Входящие фото сохраняются туда же
автоматически (см. раздел «Автоматическое сохранение фото»).

Плюс есть **универсальный** инструмент `history` — он видит историю всех модулей,
не только Telegram.

## 5. История чата: важная деталь про Bot API

Telegram **не даёт ботам серверную историю**: `getUpdates` возвращает только
апдейты за последние 24 часа, а «прочитать переписку» через API нельзя. Поэтому
история — это локальный durable-лог, который ведёт модуль:

- `.alive/history/messages.jsonl` — все входящие и исходящие сообщения;
- `.alive/history/threads.json` — каталог чатов (заголовок, тип, участники, мета);
- `.alive/modules/telegram/state.json` — offset long polling, счётчики, identity.

Практические следствия:

- история начинается с момента, когда бот был запущен (и подключён к чату);
- `historyLimitPerThread` ограничивает рост на болтливых чатах (прунинг с запасом,
  не на каждом сообщении);
- `alive history` и инструмент `history`/`telegram` работают и когда рантайм не
  запущен — они читают файлы.

## 6. Telegram-профили для нескольких агентов

Можно вручную подключить отдельного бота к агенту: создайте его через `@BotFather`,
задайте уникальную переменную окружения и выполните:

```bash
alive agents telegram researcher --token-env RESEARCHER_TELEGRAM_TOKEN
alive agents restart researcher
```

**Bot API 9.6 Managed Bots интегрированы в Alive.** Включите управление ботами для
master-бота в Mini App @BotFather, запустите master-бота Alive и выполните:

```bash
alive agents create researcher
alive agents request-telegram researcher --chat <ваш Telegram user ID>
```

Агент с инструментом `manage_agents` может отправить тот же запрос без shell:

```json
{ "action": "request-telegram", "id": "researcher", "chat": "123456789" }
```

Нужно право `agentManagement.configurePermissions` для целевого профиля (и его ID
в `targets`). `chat` — положительный ID личного чата оператора, не группы.
Оператор должен предварительно написать master-боту; master-бот Alive должен
работать, чтобы принять подтверждение.

Пока заявка живёт, её состояние и время истечения видны из CLI и агенту:

```bash
alive telegram managed status            # все заявки
alive telegram managed status researcher --json
alive telegram managed cancel researcher # убрать заявку и клавиатуру
```

Те же действия через инструмент `telegram`:

```json
{ "action": "managed_status", "agent": "researcher" }
{ "action": "managed_cancel", "agent": "researcher" }
```

Заявка живёт `managedBotTtlMs` — от 10 до 15 минут, по умолчанию 12. Повторный
запрос для того же агента не ошибка: возвращается уже активная заявка. После
отмены или истечения TTL можно запросить заново.

Статусы: `pending` (ждёт подтверждения), `created` (бот подключён), `expired`
(истекла; оператор получил сообщение с подсказкой про BotFather), `failed`
(ошибка при получении/сохранении токена, с причиной).

Запрос приходит с **inline-кнопкой** «Create bot for …»: она не добавляет
reply-клавиатуру над полем ввода, поэтому не может залипнуть в composer. Bot API
пока поддерживает `request_managed_bot` только на reply-клавиатуре, поэтому
нажатие inline-кнопки присылает отдельное сообщение с одной нативной кнопкой
создания — её обработка начинается с callback path. После создания, отмены,
истечения и ошибки модуль явно отправляет `reply_markup: { remove_keyboard: true }`
с короткой подписью о том, что кнопка убрана. Если клиент так и не прислал
`managed_bot_created`, по истечении TTL оператору приходит сообщение: возможно,
клиент не поддерживает managed bots, и предлагается создать бота через
`@BotFather`.

Подтвердите запрос в личном чате с master-ботом. Alive обработает `managed_bot_created`,
получит секрет методом `getManagedBotToken` и сохранит его **не в конфиге**, а в
`.env` рядом с конфигом агента (права `0600`); в `alive.config.json` остаётся
только `modules.telegram.tokenEnv` (имя переменной) и `enabled: true`. Токен не
публикуется в сообщениях или логах. Запустите профиль отдельным процессом:
`alive agents start researcher`.

## 7. Ограничения

- Нет webhook-режима: используется long polling. Один процесс на токен
  (`getUpdates` конфликтует сам с собой).
- Фото скачивается автоматически (см. раздел «Автоматическое сохранение фото»);
  документы и стикеры агент забирает по требованию через `telegram({ action: "download_file" })`.
  PDF после скачивания читается через `telegram({ action: "pdf_text" })`.
- Видео не транскрибируется; голосовые распознаются только при настроенной transcription.
- Telegram-лимиты (30 сообщений/сек, 20 сообщений/мин в группу) не соблюдаются
  специально: при 429 модуль уважает `retry_after` для polling, а отправка
  деградирует в ошибку доставки, которую увидит агент.
- Правка/удаление чужих сообщений невозможна (ограничение Telegram).

## 8. Тесты

```bash
npm run test:modules
```

Покрыто без сети: маппинг апдейтов (личка/группа/упоминание/реплай/топик/
медиа/callback/edit), разбиение длинных сообщений, парсинг тредов, клиент Bot API
(конверт, коды ошибок, `retry_after`), парсер PDF с лимитами и инструмент `pdf_text`
(скачанный файл, постраничное чтение, запрет путей вне `telegram-files`),
автосохранение фото (успех, лимит, ошибка загрузки, только самый крупный размер)
и полный цикл модуля на фейковом Bot API — от `getUpdates` до события в инбоксе,
записи в историю и отправки ответа.

Кнопки `send_message` проверяются в `npm run test:modules`: два callback-действия в
`reply_markup`, приход `data` в событии того же треда, отказ при `callback_data`
> 64 байт до вызова API, запрет `url`-кнопок в группе без флага, а также
регрессия текста и вложений. Managed Bot flow проверяется отдельно:
`npm run test:managed-bot` (статус, повтор, отмена, истечение и клавиатура, токен
в `.env` с правами `0600`, успех и причина ошибки); inline-запрос и callback path
дополнительно покрыты в `test:modules`.
